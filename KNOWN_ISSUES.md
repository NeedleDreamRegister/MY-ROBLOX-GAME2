# Состояние проверок и известные ограничения

## Исправлено 15 ноября: гора не появляется после запуска

Симптом: «Дождитесь загрузки», «Не удалось загрузить прогресс», нет добываемой горы. Журнал: `DataStoreService: StudioAccessToApisNotAllowed`, API GetAsync, Data Store DigMountainPlots_v1.

Причина: после открытия опубликованной игры Studio не имела разрешения читать/сохранять данные. Сборка участка прекращалась до появления рабочей горы. Не удалённая модель, не пустой профиль, не повод заново создавать гору.

Решение: владелец вручную включил **File → Experience Settings → Security → Enable Studio Access to API Services**, нажал **Save**, после чего выполнен новый Play. [Официальная инструкция Roblox](https://create.roblox.com/docs/cloud-services/data-stores).

Подтверждено именно в текущем облачном проекте:

- PlaceId=123243510098281, UniverseId=10776747096.
- InitialCells=67525, RemainingCells=67525, DugCells=0.
- PersistenceStatus сначала Dirty, затем **Saved**, SavedRevision=**1**.
- На снимке видно гору и обычный игровой HUD; сообщение об ошибке исчезло.
- Код не переписывали, сохранения не удаляли, гору не восстанавливали вручную. После проверки Play остановлен.

Это настройка Roblox-игры; она не переносится простым редактированием Lua. При другой игре / UniverseId доступ нужно проверять для неё. При повторной ошибке сначала смотреть точную причину в Output. Не включать аварийное создание пустого профиля и не сбрасывать аккаунт при любой ошибке DataStore.

## Прочие замечания

- В Output остаётся прежнее предупреждение `rbxassetid://203785492` о несовпадении типа ресурса. Оно существовало до последних визуальных работ и само по себе не объясняет ошибку API сохранений.
- На отдельных запусках были сообщения Roblox о недоступных внешних ресурсах/аватаре и аналитике магазина. Не смешивать их с подтверждённой причиной отсутствия горы.
- Захват окна Windows иногда возвращает FrameArrived/window capture timed out, хотя игра видна пользователю. Это сбой наблюдения, а не доказательство остановки Studio. Нативный MCP screen_capture в последней проверке дал нормальный игровой снимок.
- В старых отчётах transport-checks описана блокировка выхода на ходу. Она отменена: актуальный код позволяет немедленно выйти пробелом.
- В раннем progression-status.md встречается план восстановления горы. Он отменён владельцем и удалён из реализации; не использовать этот пункт как задание.

## Что проверено на прошлых этапах

Отчёты v11–v17 описывают реальные локальные проверки добычи и продажи, покупок, тачки и конвейера, миграции данных, хвата инструмента и спуска. В v4 повторно проверены добыча 20, продажа 20 за 20 монет и мастерская. В v5 проверялись визуальное построение, защищённые зоны и неизменность Terrain/исходных объектов. При убирании мебели проверено, что после запуска она не появляется, а модели остаются в ServerStorage.

В чате транспорта проверялись круги с пассажиром, стоянка, посадка, управление камерой, колёса/руль, выход и свободные габариты. В последней проверке этого пакета проверялись только загрузка рабочей горы и переход сохранения в Saved — повторных покупок/добычи не было.

Не выдавать прошлые локальные проверки за полную приёмку многопользовательского режима. Одновременная игра нескольких настоящих игроков, реальный телефон и все сценарии выхода/повторного входа в опубликованной игре полностью не подтверждены. Обычная облачная загрузка и сохранение одного текущего участка теперь подтверждены SavedRevision=1; прежние отчёты про отсутствие любой облачной проверки относятся к старым этапам.

## Файлы и история

`reports/` — историческая документация, не список активных задач. Снимки v5 показывают дорогу до транспортного расширения; снимки v17 относятся к предыдущему оформлению. Снимок loading-restored.jpg относится к текущей игре. `backups/` хранит более ранние карты; не открывать их как «более новые» только из-за имени Backup3.
