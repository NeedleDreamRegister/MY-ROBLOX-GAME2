# Поэтапная миграция игровых скриптов в Rojo

**Статус:** миграция всех восьми групп выполнена после нового разрешения пользователя перенести всё необходимое. Фактические проверки, резервные копии и ограничения: `docs/rojo-migration/results-2026-11-11.md`.

**Цель:** существующие 15 игровых скриптов получают источники из файлов через Rojo без переноса объектов, изменения механик, дублирования обработчиков или публикации.

**Архитектура:** оставить имена, классы и родителей всех объектов в Explorer. Добавлять в конфигурацию индивидуальные соответствия «существующий объект → существующий файл». Папку RojoManaged оставить только для прежнего теста соединения. Не подключать целиком src или папки сервисов.

**Инструменты:** установленный C:\tools\Rojo\rojo.exe, Rojo 7.7.1; localhost 127.0.0.1:34873. Источник требований — текущая задача пользователя и AGENTS.md.

## Исходная проверка до миграции

Основная сцена Studio, PlaceId 79018924370790, Universe 10775752542. При повторной сверке после переподключения Studio показала PlaceVersion=42; это наблюдение открытой сцены, а не публикация со стороны Codex. Шаблон содержит 165 ячеек. SandPrototype включён, RunContext=Legacy; PersistenceEnabled=true, PersonalPlotsEnabled=true.

Все 15 игровых скриптов найдены ровно по одному. 14 Source совпадают побайтно с локальными файлами. У SandPrototypePlotData в Studio один дополнительный LF в конце: весь код совпадает. Это различие не исправлялось. Отдельно присутствует уже подключённый ServerScriptService.RojoManaged.RojoConnectionTest; он не входит в игровые 15.

До миграции в `default.project.json` после массива `servePlaceIds` отсутствовала запятая перед `tree`. Ошибка исправлена при выполнении группы 1; финальный файл прошёл разбор JSON и `rojo sourcemap`.

Отчёт с путями, классами, атрибутами и хэшами: docs/rojo-migration/analysis-2026-11-11.json. В отчёте нет содержимого DataStore, токенов или данных аккаунтов.

## Границы

- Не запускать синхронизацию или менять активный конфиг в рамках одного анализа.
- Не публиковать и не использовать сборку Rojo как замену полного Place.
- Не создавать второй серверный Script SandPrototype или обёртку, которая повторно вызывает Plots.Start/World.Start.
- Не изменять Source, игровые параметры, алгоритмы, DataStore names/keys/schema и поведение. Единственное согласуемое текстовое выравнивание — дополнительный LF в PlotData.
- Не управлять Workspace, Terrain, StarterGui, геометрией/моделями, RemoteEvent, деталями инструмента и игровыми данными.
- Сохранять $ignoreUnknownInstances=true на корне, сервисах, промежуточных объектах и управляемых скриптах. Эта настройка сохраняет неизвестные объекты, но не защищает ранее управляемые узлы при их удалении из конфигурации.
- Не добавлять $path на родительские папки целиком: будущий новый файл не должен самопроизвольно стать вторым серверным обработчиком.
- Пользователь и друг не редактируют одновременно один Source. После миграции группы редактировать её через общие файлы; для немигрированных объектов действуют прежние правила Studio.
- Каждый этап: Edit, согласование конкретной группы, резервная копия, предварительный diff, ограниченная синхронизация, сверка, затем свежий запуск теста. Не синхронизировать во время Play: require-кэш и существующие соединения не перезапускаются надёжно от смены Source.

## Зависимости и причины порядка

- Snapshot — чистая проверка схемы 1/массы; прямых require нет.
- AccessRules — чистая проверка Closed/Friends/Open; прямых require нет.
- PlotData → Snapshot: свежая гора и перенос старого общего профиля.
- CoopData → Snapshot: схема 2, счётчики вкладов/импорта, монотонность наград.
- FindData → CoopData: схема 3, положение находки, выдача и коллекция.
- SaveSession → Snapshot: атомарная запись, lease/CAS; в личном режиме получает валидатор FindData и переход Finds.Advances снаружи.
- Economy не требует модулей; после Init регистрирует игроков и начисляет/продаёт песок, публикует SandPrototypeState. Factory Create изолирует владельцев; legacy default instance сохраняется.
- ClientContext не требует модулей; читает SandPrototypeMountain, SandPlots и SandPrototypePermissions.
- HUD/Feedback/Visits/Probe → ClientContext. Они используют PlayerGui, SandPrototypeState и SandPrototypeDig. Visits дополнительно ждёт SandPrototypeVisit/SandPrototypeAccess, которые создаёт сервер при запуске. Отсутствие этих двух RemoteEvent в Edit не является основанием создавать дубликаты.
- World → Economy.Create, SaveSession, CoopData, FindData. Start создаёт соединения добычи и станций, ведёт геометрию/награды/запись конкретной горы.
- Plots → World, PlotData, CoopData, FindData, AccessRules. Start создаёт участки, права/посещения и синхронизацию подтверждённых наград.
- SandPrototype → Plots.Start при PersonalPlotsEnabled=true. Ниже сохранена старая общая ветка → Economy/SaveSession/Snapshot. Потеря атрибута PersonalPlotsEnabled переключит ветку — поэтому запуск и метаданные переносятся последними.

Сохраняются пространства DataStore: DigMountainPlots_v1 / player_USERID и историческое DigMountainPrototype_v1 / shared_world_v1. Их записи не входят в rbxl и не переносятся через Rojo.

## Подготовительный этап после подтверждения первой группы

1. Пользователь завершает Play и согласует с другом короткое окно без параллельных правок.
2. Отключить плагин Rojo, остановить соответствующий serve на 34873. Не трогать посторонний тестовый сервер 34872.
3. Сохранить полную текущую сцену через Download a Copy под новым именем; не перезаписывать прежний backup. Дополнительно снять Source/класс/атрибуты/Enabled/RunContext всех 15 объектов и контрольные количества объектов. Старый ExportCheckpoint.luau ожидает 15 скриптов, а с Rojo-тестом их 16: не запускать его вслепую и не удалять тест ради прохождения assert.
4. Заново сверить основную сцену и файлы: текущий отчёт — снимок, а не замена проверке перед записью.
5. Сохранить исходный конфиг как исторический текст, исправить запятую и добавить только два соответствия группы 1. Не включать следующие группы.
6. При переносе черновика из docs/rojo-migration в корень заменить пути ../../src/... на src/.... Не копировать черновик целиком в корень без пересчёта относительных путей.
7. Проверить JSON и sourcemap установленным Rojo. Корень/сервисы остаются с ignoreUnknownInstances=true; servePlaceIds сохраняет [0,79018924370790], placeId/gameId не назначаются. emitLegacyScripts=true сохраняет классы Script/LocalScript.
8. Запустить serve и подключить плагин в режиме с предварительным просмотром изменений. Новых игровых объектов быть не должно: существующие узлы сопоставляются по прежним именам и классам.
9. Если Rojo предлагает удалить/заменить/дублировать объект, поменять родителя, Terrain/модель/Tool или свойства вне списка — отменить операцию и исследовать расхождение.

## Группы и приёмка

### 1. Snapshot и AccessRules — 2 модуля

Небольшие чистые функции без запуска сервера, DataStore и обработчиков. Неактивный черновик: docs/rojo-migration/stage-1.project.json. Проверен командой rojo sourcemap на 7.7.1: прежний тест и ровно два существующих ModuleScript.

Проверки: точное совпадение двух Source, классов и числа экземпляров; прежние 165 шаблонных ячеек/остальные скрипты на месте. Запустить имеющиеся проверки Snapshot и разрешений на свежих временных копиях модулей; не требовать повторно игровые фабрики в живой сессии. Затем короткий штатный Play/Stop с обычной загрузкой, без добычи для этой группы. Не обещать успешные runtime-тесты до фактического запуска.

### 2. PlotData, CoopData, FindData — 3 модуля

Сначала согласованно добавить в локальный PlotData один конечный LF, чтобы он побайтно совпал с текущим Studio Source; не переписывать код или схему. Повторить сверку перед применением.

Проверки: имеющиеся тесты миграций 1/2/3, сохранения массы, частичного/повторного подтверждения наград и находок на свежих копиях. Штатный Play/Stop должен восстановить прежнюю геометрию, монеты, XP, вместимость и коллекцию. Облачные данные ради миграции не сбрасывать.

### 3. SaveSession и Economy — 2 модуля

Сохраняются классы, сигнатуры и имена. Никаких новых Script, Init или вызовов Start в конфигурации.

Проверки: имеющиеся session-тесты с инъецированным хранилищем — lease, revision conflict, повтор/ошибка записи. В согласованной игровой проверке одна добыча даёт ровно 1 песок/1 XP; продажа оплачивает запас один раз, повторная продажа пустого рюкзака даёт 0. Если нужно проверять покупку, использовать изолированный непостоянный стенд; не тратить/сбрасывать рабочий профиль ради повторения апгрейда.

### 4. ClientContext и HUD — 2 скрипта

Промежуточные узлы ReplicatedStorage, StarterPlayer и StarterPlayerScripts описываются по существующим классам с ignoreUnknownInstances=true. Ни один RemoteEvent или объект StarterGui не включается.

Проверки: свежий Play; HUD единственный, показатели совпадают с сервером, свой участок выбран верно, состояния загрузки/ошибки читаются. Повторить имеющуюся проверку HUD на узком/широком viewport. Не оставлять второй ScreenGui после проверки.

### 5. Feedback и Visits — 2 LocalScript

Переносятся только источники. Эффекты и меню продолжают создаваться прежней логикой в runtime; их модели/UI в конфигурацию не попадают.

Проверки: одна подсветка/одно уведомление добычи, временные частицы удаляются; меню открывается, Домой/посещение работают; Closed/Friends/Open не обходят сервер. На двух изолированных клиентах проверить посещение и запрет/разрешение чужого копания.

### 6. SandProbeClient — 1 LocalScript внутри существующего Tool

Имя файла SandProbe.client.luau отличается от Explorer: ключ должен быть ровно SandProbeClient. StarterPack и Лопата — только существующие промежуточные объекты ($className Tool на Лопата, без $path на Tool), ignoreUnknownInstances=true. Конкретный файл задаётся в дочернем узле SandProbeClient, класс LocalScript выводится Rojo из расширения.

Не управлять Handle, Blade, GripBar, WeldConstraint, Grip и атрибутом Tool.SandPrototypeTool=true. Они остаются в сцене, а не импортируются из файлов.

Проверки: исходный Tool и детали/сварки на месте; один SandProbeClient внутри шаблона. Свежий Play выдаёт одну лопату, одиночное действие отправляет один запрос; PC и Touch работают. Эмулятор Touch проверяет управление, а не производительность настоящего телефона.

### 7. World и Plots — 2 серверных ModuleScript

Расположение SSS сохраняется для script.Parent.require. Синхронизация в Edit, затем свежий Play. Не выполнять Start вручную через MCP; этим занимается существующий SandPrototype.

Проверки: по одному набору участков и станций; копание/осыпание соблюдают массу, личные награды и разрешения работают, подтверждения помощи не дублируются, находка/музей сохраняются. Проверить два локальных клиента в изолированном стенде без рабочих записей, затем штатный повторный вход. В Edit шаблон остаётся 165. Не заменять содержимое Workspace из runtime-клонов.

### 8. SandPrototype — единственная точка запуска

Узел остаётся ServerScriptService.SandPrototype, Script, Enabled=true / Disabled=false, RunContext=Legacy. Перед применением сохранить и явно проверить PersonalPlotsEnabled=true, PersistenceEnabled=true. В конфигурации поддерживаемые атрибуты задаются через $properties.Attributes с явными Bool-значениями по формату Rojo; если атрибуты изменились или появились новые — сначала обновить снимок и согласовать сохранение всех значений. Не задавать пустую таблицу атрибутов.

Проверки: ровно один исполняемый игровой bootstrap; отдельный RojoConnectionTest только печатает строку. Полный цикл: загрузка → копание → продажа → сохранение → повторный вход; два игрока, доступ, кооперативная награда, находка, музей, HUD и инструмент. Нет второго Start или повторной оплаты. Финальный контроль всех 15 Source/классов/метаданных. Публикацию этот этап автоматически не выполняет.

## Неактивный черновик и откат

stage-1.project.json лежит вне активного дерева синхронизации и включает только первую группу; запускать его до подтверждения не нужно. Его sourcemap — локальная проверка дерева, не доказательство принятия объектов плагином. $className не задаётся одновременно с $path на отдельный файл: класс выводится из .luau/.client.luau/.server.luau и проверяется sourcemap.

Откат: сначала отключить плагин и остановить serve. Нельзя просто удалять уже управляемые узлы из JSON при подключённом плагине — Rojo может удалить их в Studio, несмотря на ignoreUnknownInstances. С отключённым Rojo восстановить Source/метаданные существующих объектов из предэтапного снимка, без создания второго экземпляра. Затем подготовить валидный конфиг предыдущей подтверждённой стадии и проверить diff при новом подключении. Если целостность сцены нарушена — работать с отдельной полной резервной копией; автоматически заменять опубликованный Place нельзя.

Rojo-откат кода не откатывает DataStore. В этой миграции не меняется схема или содержимое сохранений; неоднозначную запись исследовать отдельно, не подменять старым профилем.

## Согласование и дальнейшая совместная работа

Первоначально план предусматривал отдельное подтверждение каждой группы. Затем пользователь явно разрешил исправить конфиг и перенести всё необходимое. Группы выполнены последовательно, с проверками каждой; результаты приведены в отдельном отчёте.

Другу передавать одну и ту же версию общего дерева файлов/конфига. Для одной совместной Studio-сцены в каждый момент один согласованный источник live sync: не подключать два Rojo из разных локальных копий к одной редактируемой сцене. Права Team Create остаются прежними. Локальные модели/карта по-прежнему ведутся в Studio. Механика, баланс и оформление — отдельные последующие задачи после завершения миграции.
